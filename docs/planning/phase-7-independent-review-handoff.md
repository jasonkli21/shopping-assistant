## Findings

1. **P1 — Restart recovery can leave active runs stranded indefinitely.** `research/supervisor.py:103`, `jobs.py:289,331`, `main.py:75` (all backend paths below are under `apps/api/src/shopping/`). Recovery runs once at startup. A just-crashed worker's unexpired job is neither recovered nor dispatched; nothing revisits it when its lease expires. Startup also stops dispatching when capacity fills and never drains the remainder. Dispatch failures and unexpected runner exits have the same absence of follow-up. The project then remains research-active and the UI cannot retry it. **Fix:** give the lifespan-owned local runner a bounded way to revisit expired ownership and drain saved dispatchable work as capacity frees, including initially unavailable storage; retain the manual runner. Respect other live owners. The 60-second lease also consumes the entire default 60-second deadline (quick is 45): reconcile recovery timing with bounded deadlines, and terminate expired work honestly rather than leaving it active. **Validate:** restart immediately after a claim, recover after expiry without another restart, more queued projects than capacity, dispatch failure, startup storage recovery, default-deadline expiry, and a recoverable run with remaining budget.

2. **P1 — Lease expiry does not actually revoke write/completion authority.** `research/common.py:92`, `jobs.py:189`. `_lock_live_run` checks only token equality; `complete_job` does not check lease expiry. Until reclaim changes the token, an expired worker can commit sources, claims, offers and terminal state. The later heartbeat is not a transactional substitute. **Fix:** validate live job ownership and expiry in the same short transaction as each worker mutation, with a consistent lock order; reject completion after expiry even without a replacement worker. **Validate:** pause a worker beyond expiry, finish I/O before reclaim, and attempt each persistence/completion path; repeat after reclaim and cancellation. A focused review probe confirmed the common guard accepts token equality without inspecting a lease.

3. **P1 — Job locking has opposing orders and can deadlock cancellation/reclaim.** `research/jobs.py:63,157,189,245,289`. Claim/cancel acquire run then job; heartbeat/complete/recovery acquire job then run. For example, cancellation holds the run waiting for the job while heartbeat holds the job waiting for the run. **Fix:** enforce one lock order across these paths and worker writes. **Validate:** PostgreSQL barriers overlapping heartbeat with cancel, reclaim and recovery, and completion with cancel; assert no deadlocks and one valid final owner/state.

4. **P1 — Resuming product research repeats completed retrievals and can abandon unfinished extraction.** `research/product_execution.py:149–350`, `product_persistence.py:386`, `jobs.py:373`. After reclaim, saved search results are selected again without consulting completed source/extraction state. Completed pages consume source/page budgets a second time; a crash after retrieval but before extraction can therefore exhaust the source cap before any claims are extracted. Offer URLs with any non-null offer status, including failures, are instead treated as already processed. **Fix:** resume from persisted per-target/source stage outcomes, skip completed work, and continue extraction from stored snapshots where safe. Apply a bounded policy to retryable/uncertain stages. One coarse durable dispatch job is acceptable if these checkpoints are reliable. **Validate:** crash after retrieval, after extraction persistence, between sources and after an offer failure; retain completed observations, consume only justified remaining budget and avoid duplicate provider calls/offers.

5. **P2 — Run and durable job terminal states can permanently diverge.** `research/supervisor.py:135–166`, `jobs.py:92,307`. Workflow finalization commits a terminal run before job completion. A crash in between leaves a running job/attempt; both reclaim and recovery refuse terminal runs, so this record never settles. **Fix:** finalize the dispatch job and run atomically where possible, or reconcile terminal runs with unfinished jobs without repeating external work. **Validate:** crash immediately after the run's terminal commit and before `complete_job`; restart should reconcile the job and attempt once, including correct failure/partial semantics.

6. **P1 — An offer refresh can succeed while every offer extraction fails.** `research/product_persistence.py:604,677`. `finish_product_research` counts retrieved pages and retrieval/stage errors, but ignores `offer_status`. A retrieved page with `identity_mismatch`, `unsupported` or `no_offer` makes an offer-only target/run succeed despite saving no offer. Combined refresh also hides failed required offer work behind successful claims. **Fix:** derive refresh success/partial/failure from requested outcomes, preserve previous offers, and expose unavailable/unsupported outcomes honestly. **Validate:** valid HTML without Product data, no offer, mismatched variant, extraction failure, mixed good/bad offers and successful claims plus failed offers. A focused mock-persistence probe reproduced target/run `succeeded` with one retrieved page and no saved offer.

7. **P1 — Targeted refresh replaces current project fit with an assessment that omits retained evidence.** `evidence/assessment.py:101–120`, `research/product_persistence.py:745`; downstream `evidence/reads.py` and `comparisons/service.py:499`. Assessment uses only snapshots retrieved in the new run. Offer-only refresh generates a new assessment containing retailer-page claims or no claims, dropping prior validated specifications/testing. Refreshing a missing dimension similarly drops untouched dimensions. The latest assessment then becomes the product/comparison fit source. **Fix:** define the effective evidence set for partial refresh: retain applicable prior validated evidence, integrate refreshed observations, and explicitly handle contradictory/superseded versions without mutating historical assessments. **Validate:** supported runtime assessment → offer-only refresh retains runtime fit; add one missing dimension without losing others; contradictory refreshed claim; requirement and catalog revisions change during refresh; old comparisons remain readable/stale until regeneration.

8. **P2 — Unchanged-content refresh recharges extraction and falsely reports no grounded claims.** `research/product_execution.py:690`, `evidence/service.py:151–195`, `research/product_persistence.py:776`. Every retrieval invokes AI extraction even when its snapshot already has validated extraction. Claim dedup then creates zero rows, and finalization uses `claims_created == 0` to flag `no_grounded_claims`, even though reused claims appear in the assessment. Reads/assessments also select all claims for a snapshot without an extraction-version policy, so simply re-extracting after a task update does not cleanly invalidate old output. **Fix:** distinguish usable/reused claims from newly inserted claims; reuse completed validated extraction when task/prompt/schema versions match, and record/select the applicable version when they change. Preserve failed/empty extraction outcomes explicitly enough to make this decision. **Validate:** identical page refresh makes no redundant extraction call, creates a new retrieval observation, preserves claim IDs and reports success; changed task version re-extracts and does not silently mix obsolete interpretations.

9. **P2 — Historical offer rows crowd out distinct refresh targets.** `research/commands.py:439`, `product_execution.py:396–405`. Planning takes the latest 12 offer observations, sorts historical stale rows first, then slices to the source cap before URL deduplication. Repeated observations for one listing can fill the slice and exclude another retailer; an old row can cause a currently fresh URL to be prioritized as stale. **Fix:** group by normalized listing identity, use each listing's latest observation for freshness, and apply target limits after deduplication/filtering. **Validate:** multiple observations of one URL plus other retailers, a stale old row with a fresh successor, excluded URLs and cap boundaries.

10. **P2 — Source targeting is enforced against query labels/request URLs, not actual sources.** `research/product_execution.py:166–183,245–269,405–436`. A manufacturer query can return a retailer and pass the source-class filter; classification after retrieval is not checked against allowed classes. Allowed URLs can redirect to excluded/out-of-scope domains. **Fix:** distinguish requested query class from verified source class, enforce domain policy through redirects/final destinations, and avoid using disallowed sources as target evidence. Preserve retriever SSRF checks and explain rejected sources. **Validate:** wrong-class search hit, excluded subdomain, allowed-to-excluded redirect, and genuine allowed source; neither extraction nor offer persistence should bypass the saved targets.

11. **P2 — Deep source selection can spend its entire cap on the first query/class.** `research/product_persistence.py:285`, `product_execution.py:149–190`. Results are query-ordered and selection fills the cap greedily. Four different domains from the manufacturer query fill the default deep cap before any independent test/community query is considered; quick's two sources have the same issue. `(query_class, host)` also permits the same publisher across classes and does not establish independence. This predates part of Phase 7 but directly undermines its source-diversity goal. **Fix:** use a small bounded selection policy that allocates coverage across useful requested classes/dimensions, uses actual classification, and avoids claiming syndication independence from host differences alone. **Validate:** many first-query results plus useful later-class results, same publisher across classes and syndicated excerpts; assert coverage and call counts.

12. **P2 — Retry UI does not preserve an exact uncertain command or recover correctly from revision conflicts.** `apps/web/src/features/discovery/DiscoverPage.tsx:254`, `apps/web/src/features/products/ProductResearch.tsx:191`. Only an in-memory request key is retained; revision and source run are read anew on each click. After a lost acknowledgement, project edits or selecting another run can reuse the key for a different command and cause a permanent conflict. Reload loses the key, allowing duplicate accepted work. Discover also never refreshes the project after retry's revision conflict. **Fix:** retain the complete pending retry command keyed by project/source run, replay it exactly on ambiguous outcomes, and clear/refresh on definitive pre-acceptance failures. Reset state on target changes. **Validate:** lost acknowledgement + edit/reload, failed retry + switch run/product, revision-conflict retry and capacity rejection; one accepted run per command.

13. **P2 — Offer refresh does not refresh the product's visible offer queries.** `apps/web/src/features/products/ProductResearch.tsx:119–207`; `ProductDetailPage.tsx:70,131`. Terminal research invalidates evidence only; `product-offers`, product detail and project-product offer caches remain unchanged. The user can see a successful refresh beside old prices until another refetch. If an older assessment was selected, starting new research also retains its `selectedRunId`, leaving latest assessment and displayed sources out of sync. **Fix:** on completion invalidate affected catalog/offer views and deliberately reset or preserve a coherent selected history context. **Validate:** refresh changes price/availability and immediately updates offers and decision inputs; start refresh while viewing old history and verify assessment/source/run consistency.

14. **P2 — Freshness policies disagree across planning and decision UX.** `research/commands.py:342,430`, `evidence/reads.py:37`, `apps/web/src/features/products/ProductDetailPage.tsx:268`, `comparisons/service.py:364`. Deep planning uses 12 hours/180 days/30 days; evidence reads use 24 hours/365 days/90 days; offer UI flags age only after seven days, and comparison offer cells report old amounts as known without age handling. A listing can need refresh while the decision UI presents it as current. **Fix:** centralize an explicit data-class freshness policy, distinguish run planning thresholds from displayed freshness if intentional, and carry freshness/observation time into offer decision cells. **Validate:** boundary ages for both modes, undated sources and unchanged-content retrieval; product, evidence and comparison views must explain consistent freshness.

15. **P2 — Default fake planning rejects a supported three-product deep run.** `integrations/personal_ai/fake.py:373–413`, `research/product_task.py:193`. The default snapshot allows five classes; the fake emits five queries for product 1 and three for product 2 under the eight-query cap, omitting product 3. Validation requires every selected target. **Fix:** reserve at least one query per target before adding class depth. **Validate:** three selected products at default limits, minimal query budget equal to target count and restricted classes. Direct review probe produced `[5, 3, 0]` queries and `product research plan must cover every selected target`.

16. **P2 — Discovery planning has no persisted external-call intent/budget checkpoint.** `research/supervisor.py:236–260`, `jobs.py:373`. Product planning records a stage attempt before AI I/O; discovery planning does not. A crash before `save_plan` causes another AI call on reclaim without marking the original call uncertain, retaining its request metadata or counting it against the AI-call budget. A crash after successful product planning but before `save_product_plan` similarly discards the plan output and repeats planning. **Fix:** persist bounded planning intent and reusable validated output before advancing, with explicit uncertainty/budget policy; use the shared execution path rather than another executor family. **Validate:** crash before response, after response persistence and before query creation for both run types; saved plans resume without extra charges where preventable, uncertain calls remain inspectable.

17. **P2 — Required Phase 7 regression and quality evidence is missing.** `apps/api/tests/research/`, `apps/api/tests/db/`, `apps/web/tests/`, phase plan and executor decision. No tests were added in the reviewed commits despite new leases, retries, migrations and refresh semantics. Existing tests do not exercise the new recovery path; the restart test still calls legacy `interrupt_all_unfinished`. Quick/deep are bounded but there is no labeled baseline showing improved missing-dimension/source coverage, grounding/identity preservation or added call cost; the local execution window remains unmeasured. **Fix:** add the focused tests above and apply migrations 0015–0018 against isolated PostgreSQL, including seeded prior-phase active/terminal runs, down/up and ORM drift. Complete offline UI interactions and desktop/mobile/hidden-tab retry/refresh/cancel journeys. Record quality/call-count/deadline/restart measurements honestly; live-provider checks remain opt-in and remote execution remains conditional. Test clock injection should cover expiry/retry boundaries without wall-clock sleeps. Do not mark the phase accepted from static checks.

18. **P3 — Existing frontend validation is red.** `apps/web/tests/discovery.test.tsx:210`, `DiscoverPage.tsx:733`. The test expects `Project revision 3`; the new UI renders lowercase `project revision 3` with a mode prefix. **Fix:** update the expectation to the intended visible semantics, then run the complete frontend suite. This is a test-contract mismatch, not evidence that revision data is lost.

19. **P2 — Transient retry handling stops at search calls.** `research/product_execution.py:205–350,569–805`, `supervisor.py:236–325`, `extraction/http_retriever.py:224`. Normal retrieval/AI timeouts immediately fail the source/stage or run; the durable job becomes terminal rather than retrying that safe remaining stage. Retrieval exposes HTTP status but orchestration does not distinguish 429/selected 5xx from permanent 4xx or honor their retry timing. Thus the planned bounded retry/refresh slice only works for search failures. **Fix:** apply a small persisted, stage-specific transient/permanent policy to supported retrieval and AI errors, preserving provider uncertainty and remaining call/page/byte/time budgets. Do not blindly repeat ambiguous charged AI calls; define that policy explicitly. **Validate:** retrieval 503/429 then success, permanent 403/unsupported page with no retry, supported AI transient failure, Retry-After beyond the deadline, exhausted budgets and cancellation during delay. Share retrieval policy between searched pages and prior offer pages so behavior does not drift.

## Implementation response — 2026-10-05

The review fixes are implemented in the existing local execution path. The earlier sentence saying this document was the only repository change describes the original review handoff and is superseded by this response.

- **Addressed in code:** findings 1–10, 12–16, 18, and 19. Recovery now runs as a lifespan-owned maintenance loop, drains queued dispatch work as capacity frees, respects live leases, and ends deadline-expired runs. Worker writes and completion validate the live lease, with run→job locking used consistently. Terminal runs reconcile unfinished dispatch rows. Product execution resumes from saved retrieval snapshots, reuses successful version-matched extraction, and tracks offer outcomes separately. Partial assessments retain applicable validated evidence for the exact variant. Refresh planning deduplicates normalized listing URLs before freshness and source caps. Source class and domain targets are checked against verified content and redirect destinations. Retry commands persist by project/product/source run; terminal runs refresh dependent UI caches and reset to the latest history context. Quick/deep planning thresholds and displayed freshness use shared definitions. Fake planning reserves coverage per target. Discovery and product planning persist attempts and commit validated plans with their attempts. Explicit transient page and AI provider errors receive one budgeted retry; uncertain or timed-out AI calls are not blindly repeated.
- **Finding 11:** source selection now interleaves requested classes and deduplicates publisher hosts; evidence relations label repeated wording as duplicate and explicitly leave independent corroboration unverified. This does not add a general syndicated-content detector.
- **Finding 17 remains partially unverified:** focused regression coverage was added, but the environment did not permit isolated PostgreSQL setup. Migration up/down and ORM-drift checks, PostgreSQL lock-race barriers, restart/deadline integration scenarios, browser/device journeys, and labeled quality/call-count measurements remain outstanding. The Phase 6 gate remains open; this change does not mark Phase 7 accepted.
